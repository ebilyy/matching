# 0004 — Event-source matches and manager decisions with inline projections

- **Status:** Accepted
- **Date:** 2026-10-01
- **Deciders:** gene.bilyy@gmail.com (Architect, Socratic pass of sdlc:architecture-design)

## Context

Зіставлення створюються автоматично (код, запам'ятоване рішення) і вручну (підтвердження пропозиції), скасовуються, повертаються в чергу при зміні ознак позиції (AC-11). Потрібні повна історія «хто створив / підтвердив / скасував і коли» (AC-13, AC-14), коректність при конкурентних рішеннях (PRD §6) і інваріант «ціна лише через зіставлення» (CONTEXT). Це рішення визначає модель даних модулів зіставлення, черги, цін та історії.

## Decision drivers

- QG-1: коректність — з конкурентних рішень застосовується лише перше; хибних автозіставлень ≤ 1% (аудит потребує пояснень у історії).
- AC-13, AC-14: повна історія кожного зіставлення.
- QG-3: черга p95 ≤ 1 с, рішення p95 ≤ 300 мс, масове ≤ 1 000 p95 ≤ 10 с.
- QG-2: автозіставлення 100k позицій у межах p95 ≤ 10 хв.

## Considered options

1. **Стан + журнал подій** — таблиці поточного стану, рішення через умовний UPDATE, append-only `match_event` у тій самій транзакції.
2. **Повний event sourcing** — джерело правди — журнал подій, стан — проєкції.
3. **Лише аудит-колонки** — created_by/confirmed_by/cancelled_by у таблиці зіставлень, без журналу.

## Decision outcome

**Chosen:** Option 2 — повний event sourcing. Історія й стан не можуть розійтися, бо стан виводиться з подій; конкурентність вирішується унікальністю (stream_id, stream_version). Проєкції оновлюються синхронно в тій самій транзакції (inline), щоб читання черги й цін лишалися простими SELECT.

## Consequences

**Positive**
- Історія AC-13/AC-14 і пояснення для аудиту точності — це сам журнал, без окремої логіки.
- Конкурентні рішення: друге append на ту саму версію потоку падає на унікальному індексі → 409.
- Проєкції можна перебудувати з журналу, якщо змінюється форма читання.

**Negative**
- Нова для команди парадигма (SAD §2) — ризик для бюджету 4 людино-тижні.
- Автозіставлення 100k позицій = 100k подій + оновлення проєкцій на імпорт — пряме навантаження на QG-2; потрібні пакетні вставки подій і set-based оновлення проєкцій.
- Обсяг журналу росте з кожним щоденним фідом; потрібна політика (не писати подію, якщо стан пари не змінився).

**Neutral**
- Схема подій стає контрактом між модулями зіставлення, черги, цін та історії — версіонування подій потрібне з першого дня.
